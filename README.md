# Todo Students

Обычный JavaScript + Express приложение для итоговой работы: личный список дел с PostgreSQL. Клиент общается с сервером исключительно через RESTful API: `GET` читает, `POST` создаёт, `PATCH` меняет и `DELETE` удаляет данные. Токен вводится пользователем после открытия страницы, остаётся только в памяти вкладки и не попадает в исходный код, сборку или GitHub Actions. До публикации заполните `.env` по образцу `.env.example` настоящими данными Moodle и секретами.

Сервер создаёт `id`, `ownerLogin`, `createdAt` и `done=false`; клиент не может их подменить. Личные дела выбираются по `ownerLogin`, поэтому токен не открывает чужие записи. Для `spoon222` уже создано обязательное дело `Итоговая работа 24.10.2026: spoon222` с `runId=manual`. Карточка каждого дела показывает дату его создания, а «Обновить» повторно читает БД, что позволяет показать независимые изменения проверяющего.

## Структура и данные

`client/src/main.js` содержит отрисовку DOM и обработчики обычного JavaScript, а `client/src/services` — HTTP-сервис; `server/routes` — контракт, `services` — правила, `repositories` — SQL, `middleware` — авторизацию и ошибки. Такое разделение сохраняет DRY/KISS и не смешивает интерфейс, HTTP и PostgreSQL.

Контракт намеренно строгий: маршрут без завершающего слеша, неверный UUID, отсутствующий `runId`, лишнее поле, пустое обновление или некорректный JSON дают `400`; неверный Bearer-токен — `401`; отсутствующее дело — `404`; сбой PostgreSQL — `503`. Все API-ответы с телом имеют `application/json`, а успешное удаление возвращает `204` без тела.

| Поле API | Столбец PostgreSQL | Тип |
| --- | --- | --- |
| `id` | `id` | UUID |
| `ownerLogin` | `owner_login` | varchar |
| `title` | `title` | varchar(200) |
| `done` | `done` | boolean |
| `runId` | `run_id` | varchar(64) |
| `createdAt` | `created_at` | timestamptz, ISO 8601 UTC |

Node.js 24+ и PostgreSQL 17 используются локально; приложение совместимо с PostgreSQL 14+. `db/init.sql` создаёт изолированную таблицу `tasks`. `db/reviewer-access.sql` создаёт отдельную ограниченную роль: пароль и строку подключения передавайте преподавателю только личным сообщением Moodle, не в форуме и не в репозитории.

## Локальный запуск

```bash
cp .env.example .env
# Отредактируйте .env: Moodle-данные, API_TOKEN и DATABASE_URL
docker compose up -d
npm install
npm run dev
# http://localhost:5173, API: http://localhost:3000
```

Для проверки production-сборки выполните `npm run build`, затем `npm start`; приложение доступно на `http://localhost:3000`. Команды `npm test` и `npm run build` выполняются CI. CD настроен как ручной GitHub Actions workflow: до готовности nginx его не запускайте. Он требует secrets `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_PATH`; `.env` остаётся на сервере. Конфигурация nginx находится в `nginx/`; сначала выпустите сертификат для `todo.simakov.space`, затем проверьте `nginx -t` и только после локальной проверки запускайте CD.

Выбран PostgreSQL на собственном VPS: это предсказуемый, где доступны отдельные роли и полный контроль над таблицей. Решение основано на наибольшем опыте работы с PostgreSQL — как коммерческом, так и учебном.
